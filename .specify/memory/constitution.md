# PythonSDD Constitution

## Core Principles

### I. 可運作的漸進式學習

每項功能 MUST 拆成可執行的小步驟，且每一步都要讓程式可以啟動，或讓遊戲保有
可操作的最小流程。新功能 MUST 先完成一個可見的最小垂直切片，再逐步增加規則、
物件、畫面或關卡。除非規格證明必要，否則不得為了展示複雜技術而加入目前需求不
需要的框架、設計模式或第三方套件。

理由：目前專案已從基本函式、迴圈與條件判斷，逐步發展到 Pygame 物件、碰撞、
生命值與關卡。保持每一步可執行，能讓錯誤容易定位，也能讓學習成果持續累積。

### II. 清楚的 Python 結構與命名

新建或修改的程式碼 MUST 遵守一致的 Python 命名：類別使用 PascalCase，函式、
方法與屬性使用 snake_case，常數使用 UPPER_SNAKE_CASE。每個類別或函式 MUST 有
清楚且單一的主要責任；當邏輯開始跨越多個遊戲物件或狀態時，MUST 以函式或類別
拆分，而不是繼續堆疊在主迴圈中。MUST 明確傳入依賴的資料，並避免為新邏輯增加
不必要的隱藏全域狀態。

既有 Day1 與 Day2 練習檔可以保留其當時的寫法，作為學習歷程；只有在新增或修改
該檔案時，才必須把涉及的程式碼逐步對齊本原則。

理由：目前程式已開始使用 `Brick`、`Paddle`、`Ball` 與 `Obstacle` 等類別。統一
命名、建構子參數與方法責任，可以降低未定義變數、初始化不一致及漏呼叫方法等錯誤。

### III. 明確的遊戲迴圈與狀態

每一幀的 Pygame 流程 MUST 維持清楚順序：控制幀率、處理事件、讀取輸入、更新遊戲
狀態、處理碰撞、繪製畫面、更新顯示。碰撞判定 MUST 發生在物件移動之後、畫面繪製
之前。`lives`、`level`、`launched`、`game_over` 等狀態 MUST 有明確的所有者與
可追蹤的轉換條件；每個新增狀態 MUST 定義進入、離開、重設或重新開始的行為。

新增或修改的邊界行為 MUST 被明確處理，包括球碰到視窗邊界、球漏接、磚塊消失、
障礙物碰撞、生命歸零與關卡完成。所有離開路徑 MUST 能正常結束 Pygame 資源。

理由：Day2 已經具備發射、碰撞、生命值、遊戲結束與升級等狀態；固定的更新順序
能讓每項規則有清楚的位置，避免畫面、物理與狀態互相覆蓋。

### IV. 以可重現驗證確保正確性

每次新增或修改功能 MUST 同時完成程式檢查與手動冒煙測試。程式檢查至少 MUST
涵蓋修改檔案的語法或編譯檢查，以及匯入所需套件的檢查。手動測試 MUST 覆蓋正常
流程、控制方式、退出方式，以及該功能的至少一個邊界或重設情境。

碰撞、計分、生命值、關卡轉換等純邏輯 SHOULD 優先放在可用固定輸入重複驗證的小
函式中；目前不要求為每個 Pygame 畫面建立完整自動化測試。若選擇不拆出純邏輯，
規格或開發紀錄 MUST 說明原因。每個錯誤修正 MUST 先描述重現方式，再確認原問題
已消失且未引入新的狀態錯誤。

理由：互動視窗不適合只依賴自動測試，而目前的學習重點是把程式跑起來並理解行為。
可重現的手動步驟搭配小型邏輯檢查，能在不增加過重工具負擔的情況下建立正確性習慣。

### V. 可讀、可除錯、可維護的遊戲程式

新加入的遊戲平衡值、尺寸、速度、顏色與時間 MUST 使用有意義的常數或集中設定；
同一數值重複使用時不得散落成無名稱的 magic number。註解 MUST 說明原因、規則或
不直觀的限制，不得只重述程式語法。暫時性的除錯輸出或測試數值 MUST 在交付前移除，
或清楚標示其用途與保留原因。

交付前 MUST 消除涉及範圍內的未定義名稱、建構子與呼叫參數不一致、漏呼叫方法、
無法到達的狀態分支與未處理的退出路徑。修改 MUST 保持範圍集中，不得把學習功能的
小改動混入無關的大型重構；若重構確實必要，規格 MUST 說明目的與驗證方式。

理由：目前程式以清楚的區塊註解和集中設定開始，但也出現過初始化、作用域與方法
呼叫容易出錯的情況。可讀性與小範圍變更能讓除錯成為學習的一部分，而不是額外負擔。

## 專案背景與技術限制

本專案是以 Python 與 Pygame 建立的循序學習專案，現有能力基線包括：

- 基本函式、變數、條件判斷、迴圈、串列與字典。
- Pygame 初始化、視窗建立、事件處理、鍵盤輸入、幀率控制與基本繪圖。
- 使用類別表示磚塊、擋板、球與障礙物。
- 實作簡單的移動、邊界反彈、矩形碰撞、生命值、遊戲結束與關卡流程。

後續設計 MUST 以這個能力基線為起點，先強化函式、類別、狀態與除錯能力，再引入
更進階的架構。除非有明確學習目標與規格理由，否則不得引入非必要的非同步程式、
複雜框架、外部服務或過度抽象。

`requirements.txt` 是專案依賴的唯一來源，目前固定使用 `pygame-ce==2.5.8`。
新增或升級依賴 MUST 同時更新該檔案，並在規格或變更說明中記錄用途與影響。既有
練習檔是可比較的學習快照，不要求在建立本憲章時一次性回頭重構全部內容。

## 開發流程與品質門檻

非單純的練習修改 MUST 依照以下流程：

1. 用 `$speckit-specify` 描述使用者可觀察的行為、限制與驗收條件；小型練習可以使用
   同等內容的短規格與檢查清單。
2. 用 `$speckit-plan` 決定資料結構、Pygame 流程與實作邊界，再用 `$speckit-tasks`
   拆成可逐項完成的任務。
3. 先實作最小可運作切片，完成一項就執行相應的程式檢查與手動測試。
4. 在交付前檢查差異範圍、狀態重設、退出路徑與規格驗收條件；若仍有未完成項目，
   用 `$speckit-converge` 補列後續任務。

每個功能交付 MUST 通過以下品質門檻：

- 修改的 Python 檔案沒有語法錯誤、未定義名稱或明顯的參數不一致。
- 遊戲可以啟動，正常路徑可操作，Escape 或關閉視窗可以結束。
- 受影響的控制、碰撞、邊界與狀態轉換已按規格驗證。
- 重新開始、遊戲結束或進入下一關時，不會沿用不應保留的舊狀態。
- 變更只包含本次功能所需的檔案；無關的格式化或重構必須另行處理。

目前階段不強制導入 pytest 或完整 TDD 流程；當可獨立驗證的純邏輯增多時，MUST
逐步增加輕量測試或固定輸入檢查，以提升回歸信心。

## Governance

本憲章是 PythonSDD 新功能與修正工作的專案級規則來源。若既有練習程式與本憲章
衝突，新的修改 MUST 遵守本憲章；既有檔案不因憲章採納而被要求一次性重寫。

憲章修訂 MUST 遵循以下程序：

1. 在本檔案中提出變更，說明動機、受影響的原則、相容性影響與驗證方式。
2. 由專案擁有者確認變更符合目前的學習目標與技術範圍。
3. 更新檔案頂端的 Sync Impact Report、版本號與最後修訂日期。
4. 檢查所有原則仍可被程式碼檢查、手動測試或開發流程驗證。

版本遵循語意化版本：移除或重新定義既有原則、造成不相容的治理變更時增加 MAJOR；
新增原則、章節或實質擴充要求時增加 MINOR；只有澄清文字、修正錯字或非語意調整時
增加 PATCH。每次功能交付或檢視 MUST 以本憲章的品質門檻檢查合規性；若有例外，
必須記錄原因、風險、補償措施與預計重新檢視時間。
